# team-1-project
KDT14기 1팀

## 주제

**자동차 취급설명서 기반 RAG 질의응답 시스템 — 파워트레인·차종별 비교 서비스**

현대·기아 차량 5종의 취급설명서 PDF를 넣고, 사용자가 *"계기판에 이 경고등 떴는데 뭐야?", "엔진오일 교환주기는?", "급속충전 시간은?"* 같은 질문을 하면 근거 문장과 함께 답하는 시스템.

### 대상 문서 (5권)

| 차량 | 파워트레인 | 차체 |
|---|---|---|
| 아반떼 | 가솔린 | 세단 |
| 아반떼 하이브리드 | 하이브리드(HEV) | 세단 |
| 아이오닉6 | 전기차(EV) | 세단 |
| 투싼 | 디젤 | SUV |
| 넥쏘 | 수소차(FCEV) | SUV |

> 5권으로 **5대 파워트레인(가솔린·디젤·하이브리드·전기·수소)을 전부 커버**하는 것이 이 주제의 최대 강점.

## 주제 선정 이유

1. **데이터 확보 초쉬움** — 현대 공식 다운로드 센터에서 취급설명서 PDF 무료 배포.
2. **정답이 명확** — 수치·주기·절차 위주라 근거 문장 추출이 쉽고 BERTScore가 제대로 작동.
3. **표가 많아 청킹 실험이 살아남** — 정비 주기표·규격표·경고등 목록. 표가 청크에서 잘리면 답이 무너지므로 성능 차이가 눈에 보임.
4. **5대 파워트레인 전부 커버** — 가솔린/디젤/HEV/EV/수소 → 문서 간 내용 차이가 커서 비교·할루시네이션 실험이 자연스럽게 나옴 (예: EV에 "엔진오일 교환주기?" → "해당 없음" 나와야 정상).
5. **유니크 + 실용** — 남들 잘 안 하고, 실제 운전자에게 바로 쓸모 있음.

## 시스템 기능 구조 (파이프라인)

```
[1] PDF 로드      5종 취급설명서 로드 (텍스트 + 표 추출)
        ↓
[2] 청킹          chunk_size / overlap 설정, 표 전처리, 차량 메타데이터 태깅
        ↓
[3] 임베딩        임베딩 모델로 벡터화
        ↓
[4] 벡터스토어    FAISS / Chroma 저장 (차량명 metadata 포함)
        ↓
[5] 검색          질문 임베딩 → top_k 유사 청크 검색 (유사도 알고리즘)
        ↓
[6] 프롬프트 구성  검색 문맥 + 질문 → 프롬프트 템플릿
        ↓
[7] LLM 답변      HuggingFace LLM / API 모델로 생성
        ↓
[8] 평가          BERTScore, 응답시간, Hallucination, 사람 평가
```

## 목표

- **최종 목표**: 5종 취급설명서 기반 RAG 질의응답 시스템을 LangChain으로 구현하고, LLM·프롬프트·벡터스토어·청킹 설정을 바꿔가며 어떤 조합이 가장 정확한 답을 내는지 비교 평가한다.
- **세부 목표**:
  1. 파워트레인이 다른 차량 간 질문에서 문서 구분 검색이 정확한가
  2. 표에 담긴 정보(정비 주기 등)를 잘 검색·답변하는가
  3. 할루시네이션(엉뚱한 차량 정보 혼입)을 얼마나 억제하는가

## 팀 구성 & 역할 분담 (4인 1팀)

| 담당 | 역할 | 파이프라인 구간 |
|---|---|---|
| **A (팀장)** | 프로젝트 총괄 + 평가체계 구축 + LLM 모델 비교 | [7][8] |
| **B** | 문서 로드·청킹·표 전처리 | [1][2] |
| **C** | 임베딩·벡터스토어·검색 | [3][4][5] |
| **D** | 프롬프트 엔지니어링 | [6] |

발표는 4명이 각자 자기 실험을 5분씩(총 20분) 담당.

## 실험 항목 (4개 — 평가표 4축 매칭)

### ① RAG / Evaluation — 담당 A

- **내용**: HuggingFace LLM 여러 개(예: Qwen2.5, SOLAR, EEVE) + API 모델(ChatGPT/Claude/Upstage)을 같은 조건에서 비교. 평가 데이터셋·BERTScore 자동화 구축.
- **변수**: LLM 모델
- **답할 질문**: *"어떤 LLM이 가장 좋은 답변을 내는가?"*

### ② Document Retrieval — 담당 B

- **내용**: PDF 로더 비교(PyPDF vs PDFPlumber), chunk_size·overlap·top_k 그리드 실험, 표를 마크다운으로 변환했을 때 효과.
- **변수**: chunk_size / overlap_size / top_k / 표 전처리 방식
- **답할 질문**: *"chunk_size·overlap·top_k가 답변 품질에 어떤 영향을 주는가?"*

### ③ Semantic Search — 담당 C

- **내용**: 임베딩 모델 비교(ko-sbert vs bge-m3 vs multilingual-e5), 벡터스토어 비교(FAISS vs Chroma), 검색 방식 비교(cosine similarity vs MMR).
- **변수**: 임베딩 모델 / 벡터스토어 / 유사도 알고리즘
- **답할 질문**: *"어떤 벡터스토어·검색 방법이 더 좋은 답변을 얻는가?"*

### ④ 프롬프트 엔지니어링 — 담당 D

- **내용**: 같은 모델에 프롬프트 3종 비교 — (기본) / (역할 부여형: "너는 자동차 정비 전문가다") / (제약형: "문맥에 없으면 '해당 정보 없음'이라고 답해라"). 할루시네이션 억제 효과 측정.
- **변수**: 프롬프트 템플릿
- **답할 질문**: *"같은 모델에 프롬프트를 다르게 주면 성능이 어떻게 달라지는가?"*

> **변수 통제**: 각자 자기 변수만 바꾸고 나머지는 팀 공통 베이스라인 고정.
> 베이스라인 예시 — `LLM=Qwen2.5-7B / chunk=512 / overlap=50 / top_k=3 / 임베딩=bge-m3 / 벡터스토어=FAISS / 유사도=cosine / 기본 프롬프트`

## 평가 지표

- **BERTScore (필수)** — 생성 답변과 정답(reference)의 의미 유사도.
- **응답 시간** — 질문당 latency (모델·설정별 비교).
- **Hallucination 발생률** — 엉뚱한 차량 정보 혼입·없는 사실 생성 사례 카운트. (예: 아이오닉6에 "엔진오일 교환주기" 질문 → 잘못 답하면 감점)
- **사람(팀원) 직접 평가** — 5점 척도로 정확성·자연스러움 정성 평가.

**평가 데이터셋**: 질문·정답 쌍 **10개 이상** + 각 정답의 **근거 문장(취급설명서 원문)**. 파워트레인별 질문(엔진오일/충전/수소충전 등)과 차종별 질문(3열 시트/험로모드)을 섞어 구성.
